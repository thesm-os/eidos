# How to remove stale generated output

`eidos run` adds and updates. It never deletes. This page covers
getting rid of output you no longer want.

Every command and output below is from a real session.

## Why `run` does not delete

A run cannot distinguish "this is no longer generated" from "this was
not generated by *this* invocation". You may have run against one
package, or with one plugin disabled. Deleting on that basis would
remove files the next full run puts straight back — and occasionally
files it would not.

So removal is a separate, deliberate command that consults the
manifest: the record of what the previous run claimed.

## Case 1 — you removed a directive

You deleted `// +gen:builder` from a type. The generator no longer
claims its output, but the file is still on disk.

```sh
eidos prune -dry-run ./...
```

```
would delete: /tmp/tut/blog/comment_builder.go
prune dry-run: 1 would-delete, 0 skipped
```

```sh
eidos prune ./...
```

```
deleted: /tmp/tut/blog/comment_builder.go
prune: 1 deleted, 0 skipped
```

Always dry-run first on a tree you care about. It is the same
computation, without the `os.Remove`.

## Case 2 — you moved output somewhere else

Routing changes leave the file at the old path. `prune` reclaims it —
see [route-generated-output.md](route-generated-output.md).

## Case 3 — you deleted the whole source package

This one needs a flag, and the reason is worth understanding.

```sh
rm -rf temp/
eidos check ./...
```

```
drift: temp/thing_builder.go (orphaned: source package
  "example.com/demoproject/temp" no longer exists;
  remove it with `prune -deleted-sources`)
check: 1 drifting file(s)
```

Plain `prune` will not touch it:

```sh
eidos prune ./...
```

```
prune: 0 deleted, 0 skipped
```

You have to ask:

```sh
eidos prune -deleted-sources ./...
```

```
deleted: temp/thing_builder.go
prune: 1 deleted, 0 skipped
```

**Why the extra flag.** An ordinary orphan was *observed* not to be
re-emitted: the run loaded the source package and produced nothing for
it. A source-gone orphan is *deduced* — the package could not be
loaded, and "deleted" is indistinguishable, from the run's scope
alone, from "you did not ask about it this time". `eidos prune
./sub/...` must not delete the rest of the tree's output.

The flag is you supplying the fact the run cannot: the package is
gone, not merely out of scope.

Note that `check` reports the orphan either way. The drift is never
silent — the flag only governs whether `prune` acts on it unasked.

## What `prune` refuses to delete

A file the manifest claims but which no longer carries the
generated-by marker on its first line. That means you edited it by
hand, so it is **skipped and reported**, never removed:

```
prune: 0 deleted, 1 skipped
```

This is why `0 skipped` in a normal run is meaningful output rather
than noise. A non-zero count says someone has been editing generated
files, which is the thing to fix rather than the prune.

## Wiring it into CI

`eidos check` exits `5` when output differs from disk — distinct from
`1` (bad invocation) and `2` (source errors), so a gate can tell them
apart:

```sh
eidos run ./...
eidos check ./...      # exit 5 => someone edited generated code,
                       #           or forgot to commit a regeneration
```

Orphans surface in the same check, so a deleted source package shows
up as drift rather than as a file quietly rotting in the tree.

Do **not** put `prune -deleted-sources` in CI unattended. It is the
one destructive path driven by inference, and a misconfigured pattern
that fails to load a package looks exactly like a deleted one.
