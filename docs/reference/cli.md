# CLI reference

The binary is whatever your project names it. Throughout this page it
is `eidos`; a downstream tool built on the framework substitutes its
own brand, and that brand also selects the config filename
(`.eidos.yaml` → `.<brand>.yaml`) and the generated-file marker.

Every command takes source patterns as positional arguments and
defaults to `./...` when none are given and none are configured.

```
eidos <command> [flags] [packages...]
```

## Commands

### `eidos run`

Runs the pipeline and writes generated files through the sink. The
normal invocation.

| Flag | Default | Effect |
|---|---|---|
| `-config` | discovered | Path to the config file. Defaults to `.eidos.yaml` found by walking up from the working directory. |
| `-no-cache` | `false` | Disable the build cache for this invocation. |
| `-diag-format` | `text` | Diagnostic format: `text` or `json`. |
| `-verbose` | `false` | Surface `Info` diagnostics. |
| `-quiet` | `false` | Suppress `Warn` diagnostics. |

`run` only ever adds and updates. It never deletes: an output whose
source stopped claiming it is left on disk, because a run has no way
to distinguish "no longer generated" from "not generated by *this*
invocation". Removing it is [`prune`](#eidos-prune)'s job.

### `eidos check`

Runs the pipeline through an in-memory sink and compares the result
against what is on disk. Writes nothing. This is the CI gate.

Same flags as `run`, minus `-no-cache`.

Exits `5` when output differs. Three differences are reported:

- **missing from disk** — the pipeline produces a file that is not there.
- **content differs** — the file exists with different content.
- **orphaned** — a file the manifest claims whose source package no
  longer exists. Remedy is `prune -deleted-sources`.

Header-only differences do not count as drift. The provenance trailer
carries a hash over body bytes alone, so re-running with a different
command line — `eidos run ./blog/...` against `eidos run ./...` —
produces an identical body and a different header, and the check sees
through it. Content appended *past* the end-of-generated marker does
count, which is what stops a manual edit surviving unnoticed.

### `eidos plan`

Prints what the pipeline would do — the resolved plugin order, each
plugin's declared outputs, and where each would land — without loading
sources or writing anything.

| Flag | Default | Effect |
|---|---|---|
| `-diag-format` | `text` | `text` or `json`. |

Use it to answer "why is this plugin running before that one" and "why
is this file landing here" before reaching for `explain`.

### `eidos explain`

Runs the pipeline and reports, per generated file, which plugins
contributed to it and which precedence layer supplied each routed
field — layout, package, directory, filename.

Same flags as `check`. This is the tool for "why did this file land
*there*", and it reads the same `ResolvedLayout` block the manifest
records.

### `eidos prune`

Runs the pipeline, then deletes files the previous manifest claimed
that this run no longer does.

| Flag | Default | Effect |
|---|---|---|
| `-dry-run` | `false` | Report the deletions without applying them. |
| `-deleted-sources` | `false` | Also delete outputs whose source package no longer exists. |
| `-diag-format` | `text` | `text` or `json`. |
| `-verbose` / `-quiet` | `false` | Surface `Info` / suppress `Warn`. |

Deletion is guarded on the generated first-line marker. A file the
manifest claims but which lacks that marker — because you edited it by
hand — is skipped and reported, never removed.

`-deleted-sources` is off by default because it is the one deletion
driven by *inference*. An ordinary orphan was **observed** not to be
re-emitted: the run loaded its source package and produced nothing for
it. A source-gone orphan is **deduced** from a directory that is not
there, because a deleted package cannot be loaded and so is
indistinguishable, from scope alone, from one you simply did not ask
about. `eidos check` reports the class either way, so the drift is
never silent — the flag only governs whether `prune` acts on it
unasked.

### `eidos version`

Prints the binary's version and exits.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Success. |
| `1` | Configuration or input fault — a bad flag, an unreadable config, a pattern matching nothing. |
| `2` | The pipeline ran and reported `Error`-severity diagnostics. |
| `3` | An unexpected panic the framework recovered. Please report it. |
| `4` | Cache verification failed. |
| `5` | `check` found drift against the on-disk state. |

`1` against `2` is the distinction worth wiring CI on: `1` means your
invocation was wrong, `2` means your *sources* were.

## Diagnostics

`-diag-format=json` emits one JSON object per diagnostic — severity,
position, plugin, message — for machine consumption. `text` is the
default and is positioned for a human: `file:line:col: severity:
message`.

Severity governs the exit code, not the volume: `Error` fails the run,
`Warn` and `Info` do not. `-quiet` suppresses `Warn`, `-verbose`
surfaces `Info`. Neither changes whether the run succeeded.
